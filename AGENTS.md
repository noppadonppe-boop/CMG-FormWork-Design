# AGENTS.md

## Scope
- Owner-revised objective: five distinct formwork systems (footing through-tie, column external yoke, beam side+soffit+shoring, slab soffit+shoring, wall two-sided). See `docs/OBJECTIVES.md`; it supersedes the footing/column-only scope of `CMG_Formwork_Codex_Master_Prompt.txt` while keeping its working rules (deterministic, no invented values, INCOMPLETE/NO_GO).

## Verification
- `npm test` (vitest), `npm run typecheck` (tsc -b), `npm run build`
- MCP server: `npm run mcp:build` then `node scripts/test-mcp.mjs [drawing.pdf]` (pass paths with spaces directly to node, not via `npm run`, on Windows)

## Drawing -> model -> chat workflow
- Shared, browser-safe model logic: `src/domain/scene.ts` (applyChanges, parseModelChanges, buildScene, OBJ/DXF/glTF). `src/aiElements.ts` converts AI elements to draft cases.
- UI: `SourceUpload` (ElementPicker, resume drawing across cases), `DrawingChat` (change proposals), `ModelWorkspace` + `Model3D` (SVG 3D viewer).
- Functions build: `npm run build --workspace functions`. Offline UI check: run vite with env `VITE_FIREBASE_ENABLED=false` (port 5199 is used by another app on this machine).
- Workflow v0.7 (wall/beam/slab) is gated by `src/workflowV07Flag.ts`: needs `VITE_WORKFLOW_V07_ENABLED=true` AND (Firebase off, emulators, or the explicit `VITE_WORKFLOW_V07_ALLOW_PRODUCTION=true`). The user opted in to production in the local `.env` (2 flags appended); a warning banner shows on production. Do not weaken the gate further; pass env vars to the process, e.g. `VITE_FIREBASE_ENABLED=false VITE_WORKFLOW_V07_ENABLED=true npx vite --host 127.0.0.1 --port 6173` (5210/5231 were unavailable on this machine).
- Shortcuts: `npm run dev:v07:offline` (port 6173, Firebase off) and `npm run emulators:alt` + `npm run dev:v07` (port 6174, demo emulator credentials) via `scripts/dev-v07.mjs`. Plain `npm run dev` uses `.env` (production Firebase) and therefore keeps v0.7 disabled by design.
- v0.7 with Firebase emulators: the default emulator ports (4000/4400/4500/8080/9099/9199) are held by another app's suite (`demo-boq-bbs`) — do not stop it. Use `npm run emulators:alt` (`firebase.emulators-alt.json`: auth 9109, firestore 8180, storage 9299, functions 5101, UI 4100), then run vite with `VITE_FIREBASE_USE_EMULATORS=true VITE_WORKFLOW_V07_ENABLED=true VITE_FIREBASE_PROJECT_ID=demo-cmg-formwork VITE_FIREBASE_API_KEY=demo-api-key VITE_FIREBASE_APP_ID=demo-app-id VITE_FIREBASE_STORAGE_BUCKET=demo-cmg-formwork.appspot.com VITE_FIREBASE_EMULATOR_AUTH_PORT=9109 VITE_FIREBASE_EMULATOR_FIRESTORE_PORT=8180 VITE_FIREBASE_EMULATOR_FUNCTIONS_PORT=5101 VITE_FIREBASE_EMULATOR_STORAGE_PORT=9299` (demo credentials so nothing reaches production; port 6174 used).

## Optimizer and report
- `src/domain/optimize.ts`: `optimizeLayout` (staged search, full `calculate` per trial) and `adviseLayout`; never changes sections/materials or invents capacities.
- `src/domain/titleBlock.ts`: persisted per case as `case.titleBlock` (hydrated in `main.tsx`); shared by `DrawingSet` (controlled) and `CalcReport`.
- Views in `src/drawing/views.tsx` accept `titled={false}` for reuse as report figures.
- Footing ties come from `src/domain/tieRoutes.ts` (`Result.tieRoutes`); `analyzeWaler` accepts explicit per-face `supports`. Rectangle results must stay identical (test in `tests/waler.test.ts`).
- `src/domain/sectionStock.ts` is generated by `node scripts/generate-section-stock.mjs` from `src/reference/thai-sections/*.json` (re-extract with `scripts/extract-pap-tis107.mjs` / `extract-sys-tis1227.mjs` after downloading the PDFs) plus `sections.json`/`materials.json`. `tests/section-catalogue.test.tsx` spot-checks values against the manufacturer tables. Roles: stud = TIMBER/SHS/RHS, waler = RHS/SHS/L/C/C_LIP/CHS. Optimizer only upgrades (I ≥ current); studs stay in their material.
- `Input.walerSectionId` / `studSectionId` / `studTimberGrade` (missing in old data → '' / '' / TIMBER-BOOK-SOFT). When an id is set, `validateInput` requires matching walerType (WALER_TYPE) and B/H/t; `applyChanges` fills them and manual dimension edits clear the id. walerType L/CHS require a catalogue id.
- Lateral pressure: `src/domain/pressure.ts` (`Result.pressureModel`, `r.pressure = pmax`). HYDROSTATIC default must keep legacy results identical; ACI347 = ACI PRC-347-14(21) SI eq. 4.2.2.1b; benchmarks in `tests/pressure.test.tsx`. Design Book content is transcribed from the scanned textbook (render pages with pdfjs `wasmUrl` = node_modules/pdfjs-dist/wasm/ — JBIG2 scans are blank without it).
- Plywood: `src/domain/plywoodGrades.ts` (`Result.plywood`, `Result.plywoodDesign`). `plywoodDesign` = APA V345 continuous-span checks on Table 12 effective sections (presets) or gross section (CUSTOM); benchmark = V345 Example 2 in `tests/plywood-grades.test.tsx`. Missing `plywoodGrade/plywoodSpans/plywoodFaceGrain` in stored data → CUSTOM/SINGLE/PARALLEL (also in `main.tsx` hydrate) so legacy results are unchanged. Sheet orientation in the layout follows `plywoodFaceGrain`.
- Beam (practical module, separate from v0.7): `src/domain/beam.ts` (`BeamInput` stored as `case.beam`, `calculateBeam`, `beamAdvice`, `beamFromCase` seeds unconfirmed drafts from the case footprint). Load path: soffit plywood → transverse joists (exact patch-load beam) → longitudinal bearers → shores (SWL from manufacturer, 0 = INCOMPLETE); side plywood → vertical studs → optional tie rows + twin walers. Vertical loads ACI PRC-347-14(21) §4.2.1 minimums, lateral ACI §4.2.3.2 demand only. UI `BeamWorkspace.tsx` (menus geometry/criteria/layout/results), `BeamDocs.tsx` (A3 BF-01..03 via shared `A3Set`, A4 report), views `src/drawing/beamViews.tsx` (shores drawn broken above 700 mm). Hand-check benchmarks in `tests/beam.test.ts`; full-app smoke `tests/beam-app.test.tsx` mocks `src/auth` (the app always requires sign-in).
- Slab (practical module): `src/domain/slab.ts` (`case.slab`, `calculateSlab`, `slabAdvice`, `slabFromCase`): one bay, plywood → joists (along Y) → bearers (along X) → shores at the bearer lines; interior-shore tributary load; ACI §4.2.3.2 lateral per edge direction. Shared helpers for both soffit systems: `src/domain/members.ts` (material, checker, plywood options, §4.2.1 minimums) and `src/components/FormParts.tsx` (Num, MemberPicker, ChecksTable, AdviceTable, load/plywood/material fields); report cover `ReportCover` in BeamDocs. UI `SlabWorkspace.tsx`, docs `SlabDocs.tsx` (SF-01..03), views `src/drawing/slabViews.tsx`. Tests `tests/slab*.test.*`; the full-app smoke in `tests/beam-app.test.tsx` walks both beam and slab.
- Wall (practical module): `src/domain/wall.ts` (`case.wall`, `calculateWall`, `wallAdvice`, `wallFromCase`): `system` TWO_SIDED (through ties: body Fy·Ag/Ω + assembly SWL) or SINGLE_SIDED (no ties: walers span between strongbacks at the brace stations; strongback = `proppedOverhang` pinned base + brace support + overhang; brace = concrete reaction + ACI lateral; base anchor shear + uplift §4.1.4d). Stored walls without `system` stay TWO_SIDED and unchanged. Pressure (ρgh/ACI) → plywood → vertical studs → horizontal twin walers; push-pull braces from ACI §4.2.3.1/§4.2.3.3 overturning max(1.5 H, 0.72 H²/2) with a pinned base. Shared `PressureFields` in FormParts (also used by beam). UI `WallWorkspace.tsx`, docs `WallDocs.tsx` (WF-01..03), views `src/drawing/wallViews.tsx`. Tests `tests/wall*.test.*`; the full-app smoke walks beam, slab and wall.
- AI drawing reading for all five systems: `src/aiElements.ts` (`AiElement.kind` FOOTING/COLUMN/BEAM/SLAB/WALL, `slabThickness` for beams; field meaning per kind in `AI_FIELD_LABEL` and the Functions SYSTEM_PROMPT/GEOMETRY_SCHEMA). `elementToCase` drafts unconfirmed cases (beam without a stated slab = no slab, never guessed); `createCases` in main keeps `workflowElementType` + beam/slab/wall. The upload page shows for every element. MCP: `formwork_element_check` runs the beam/slab/wall engines statelessly and can write an importable project file.
- Project Example "แปลนและรูปตัด" shows two A3 sets: first the standard construction set from the case's practical/legacy inputs (FW/BF/SF/WF, same renderer as every project, reference = project 11111 FW-01..04), then the v0.7 installation book (`src/drawing/workflowInstallation.tsx`, member colours = `src/drawing/views.tsx` C palette). Each `A3Set` print button prints only its own set (`.print-target` + print CSS). Visual QA of the book: `node scripts/render-project-example-drawings.mjs`.
- Geometry/criteria/layout pages always show the practical/legacy editors, even when the case has a v0.7 draft (v0.7 replaces only results/drawings/report); `WorkflowV07Summary` shows the stored draft read-only on geometry/layout and compares its extents with the page values. Case-bar element buttons navigate to (or offer to create) a case of that type; they must never retype the open case. `upgradeProjectExampleCase` restores example types from their canonical names. Regression: `tests/project-example-pages.test.tsx`.
- Avoid editing TS template literals through bash heredocs/`node -e` (backticks/`\d` get mangled); use the edit tool.

## Identity (rules)
- Some production Google accounts have NO email in Firebase Auth. Their profile key is the lowercased UID (client `emailKey(user.email ?? user.uid)`, Functions `managedProfile`). Firestore/Storage rules use `email() = token.get('email', uid).lower()` and reject anonymous sessions; keep it a single expression (rules evaluation budget). Test: "admits Google sessions without an email claim" in `tests/rules.test.ts`.
- Rules tests: ports 8080/9199 and 8180 may be held by other emulators; run `firebase emulators:exec --config <temp config with free ports> --project demo-cmg-formwork --only firestore,storage "npx vitest run --config vitest.rules.config.ts"`.

## MCP server (`mcp/`)
- `mcp/formwork-model.ts`: model store/revisions, 3D scene, OBJ/DXF/app-backup export; `mcp/server.ts`: MCP tools + prompt.
- Compiled with `tsconfig.mcp.json` (NodeNext) to `mcp/dist/mcp/server.js`; rebuild after changing `mcp/` or `src/domain/`.
- Registered at user level in `%APPDATA%\devin\mcp_config.json` as `cmg-formwork`; models in `artifacts/formwork-models`.
- stdout is the MCP channel: never `console.log` in the server (it is redirected to stderr).
- Results are screening only; never convert INCOMPLETE to PASS or auto-set `confirmed=true`.
